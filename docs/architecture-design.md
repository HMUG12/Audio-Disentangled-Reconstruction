# 说话 + 唱歌统一语音生成系统 · 技术设计文档

> 版本：v1.0 ｜ 日期：2026-08-06
> 定位：本项目（ADR）的顶层技术设计，依据对 2025–2026 年业界优秀开源项目的调研产出，可直接据此启动开发。

---

## 第一章 目标与范围

### 1.1 系统定位

构建**单一模型**统一支持以下三种生成模式：

| 模式 | 输入 | 输出 | 说明 |
|---|---|---|---|
| 说话（TTS） | 文本 + 参考音频（音色提示） | 自然语音 | 韵律由语言上下文自动推断 |
| 唱歌（SVS） | MIDI 音符 + 歌词 + 参考音频 | 歌声 | 旋律、节奏由 MIDI 显式控制 |
| 音色克隆 | 数秒参考音频 | — | 零样本提取音色条件，跨说话/唱歌保持同一嗓音身份 |

### 1.2 设计目标

1. 说话与唱歌**音色身份一致**：同一个人"说起来"和"唱起来"是同一个声音（支持说唱、音乐剧等中间形态）
2. 唱歌模式**旋律可控**：严格跟随 MIDI 音高与时值
3. 说话模式**韵律自然**：不受旋律条件束缚
4. 中小算力可复现：首版 0.3B 参数级，训练依托云端租卡完成

### 1.3 非目标（本期明确不做）

- 实时流式合成（二期再议，可借鉴 Qwen3-TTS 双轨流式架构）
- 大规模多语言（首期仅中、英双语）
- 完整歌曲生成（含伴奏、编曲，属于 Suno 类任务，不纳入）
- 自研语音 tokenizer / 声码器（复用开源预训练权重，见第三章）

## 第二章 总体架构（核心）

### 2.1 核心矛盾与选型决策

统一模型的根本困难在于**条件冲突**：唱歌要求旋律条件强约束（音高节奏必须跟随 MIDI），而说话的韵律应由语言上下文自由推断。若简单混合两类数据训练单一模型，旋律条件会在两种模态间产生梯度干扰，两边质量都下降。

**选型决策：采用 UniVoice 式"分解条件 + 共享流匹配 backbone"架构。**

依据：

1. **已验证的最优解**：UniVoice（arXiv 2606.05852，巨人网络+上海音乐学院，2026.6）用分解条件（内容/旋律/音色三路）+ 可学习 null melody token，0.3B 参数即在说话上追平专用 TTS（F5-TTS、CosyVoice3），唱歌上超过统一基线 Vevo1.5
2. **算力匹配**：0.3B 级 CFM 训练，4–8 卡 A800 按周计可完成，符合租云预算
3. **训练成本低**：条件流匹配（CFM/整流流）比 AR codec token 方案（Fish S2 式 Dual-AR）数据需求低、训练稳定，适合中小团队

### 2.2 模块划分

```
                    ┌─────────────────────────────────────────────┐
  文本/歌词 ──→ 音素序列 ──→ │  内容编码器 (Content Encoder)          │
                              │   - 音素嵌入（中/英字典+全局音素）      │──┐
                              └─────────────────────────────────────┘  │
                    ┌─────────────────────────────────────────────┐    │
  MIDI 音符 ────────→│  旋律编码器 (Melody Encoder)                 │    │
  （唱歌模式）        │   - 音符级嵌入：音高+时值+力度               │──┤
  null token ──────→ │   - 说话模式：可学习 null melody token       │    │
  （说话模式）        └─────────────────────────────────────────────┘    │ 条件
                                                                         │ 注入
  参考音频 ──→ ┌─────────────────────────────────────────────┐          │
              │  音色编码器 (Timbre Encoder)                   │──────────┘
              │   - 复用预训练 speaker encoder / codec 特征    │
              └─────────────────────────────────────────────┘
                              ┌─────────────────────────────────────┐
  任务位 (speech/sing) ─────→ │  共享 Backbone：DiT                  │
                              │   - 条件流匹配 (CFM) 生成声学特征     │
                              │   - 任务调制 token（无独立任务头）    │
                              └──────────────┬──────────────────────┘
                                             ▼ 声学特征（mel / codec 隐空间）
                              ┌─────────────────────────────────────┐
                              │  声码器（复用预训练，不自训）          │
                              │   BigVGAN / Fish DAC decoder         │
                              └──────────────┬──────────────────────┘
                                             ▼ 波形音频
```

### 2.3 各模块职责与设计要点

**内容编码器**
- 输入为音素序列（非原始字符），音素体系沿用 DiffSinger 规范：中/英语言字典 + 全局音素 `SP`（停顿）/`AP`（换气），支持跨语言音素合并组
- 唱歌模式下音素时长由旋律条件对齐；说话模式下时长由模型隐式建模

**旋律编码器（统一架构的关键创新点）**
- 唱歌模式：MIDI 音符序列 → 音符级嵌入（音高、时值、力度三要素）
- 说话模式：以**可学习 null melody token** 替代旋律输入。理论上等价于在条件流中对旋律变量做边缘化（marginalization），使说话韵律完全由语言与声学上下文推断——这是避免旋律条件污染说话韵律的核心机制（出处：UniVoice）

**音色编码器**
- 零样本音色克隆：数秒参考音频 → 音色嵌入
- 实现上复用预训练 speaker encoder（如 WavLM 系）或语音 codec 的声学特征，**不自训**
- 音色条件与内容、旋律条件解耦注入，保证跨模式音色一致（出处：Vevo2 的音色解耦设计）

**共享 Backbone（DiT + CFM）**
- Diffusion Transformer 主干，条件流匹配目标，整流流（rectified flow）采样
- 说话/唱歌视为同一连续流的两种条件模式，用轻量**任务调制 token** 区分，不引入独立任务头（出处：UniVoice 的 task modulation 设计）
- 首版 0.3B 参数；数据量上来后扩展至 1B

**声码器**
- 复用预训练 BigVGAN（mel 路线）或 Fish DAC decoder（codec 路线），冻结权重

### 2.4 数据流

**训练时**（每个 batch 内说话与唱歌样本混合）：

```
说话样本: 音素 + null melody token + 音色嵌入 + speech 任务位 ──→ CFM loss
唱歌样本: 音素 + MIDI 旋律嵌入    + 音色嵌入 + sing 任务位   ──→ CFM loss
```

**推理时**：
- 说话接口：`synthesize(text, ref_audio)` → 音素化 → null melody → 采样 → 声码器
- 唱歌接口：`sing(midi, lyrics, ref_audio)` → 音素化 + 旋律编码 → 采样 → 声码器

## 第三章 关键模块设计

### 3.1 语音 Tokenizer / 声学特征（复用，不自研）

| 方案 | 来源 | 说明 |
|---|---|---|
| 首选：Fish Speech 改进 DAC | fishaudio/fish-speech（开源） | RVQ 多码本，工程成熟，含完整编解码推理代码 |
| 备选：Qwen3-TTS-Tokenizer-12Hz | 阿里开源 | 12Hz 低帧率，序列更短训练更快，PESQ/STOI 指标优 |

决策依据：tokenizer 训练成本高（需大规模通用音频），开源权重已成熟，自研性价比极低。若 backbone 输出走 mel 路线，则可跳过 tokenizer，直接用 mel + BigVGAN。

### 3.2 情感与表现力控制（预留，二期）

- 借鉴 IndexTTS-2（B 站开源）的情感-音色解耦：情感嵌入独立于音色嵌入注入
- 一期仅预留条件接口（一个可扩展的条件槽位），不训练情感模块

### 3.3 歌声可控性设计

借鉴 DiffSinger 方差模型思想，将歌声参数分层处理：

| 参数 | 一期处理方式 |
|---|---|
| 音高 | 显式：由 MIDI 旋律条件强约束 |
| 时长 | 显式：由音符时值约束 |
| 能量 / 气声 / 发声 | 可选增强条件槽位（二期，对应 DiffSinger variance 的 energy/breathiness/voicing） |

### 3.4 模型规模规划

| 版本 | 参数量 | 触发条件 |
|---|---|---|
| v0.3B（首版） | 0.3B | 对齐 UniVoice 已验证规模，数据 1k–5k 小时说话 + 百小时唱歌 |
| v1B | ~1B | 数据规模上来且 0.3B 评测瓶颈明确出现在容量上 |

## 第四章 数据方案

### 4.1 数据来源

**说话数据（目标 1k–5k 小时）**

| 数据集 | 规模 | 说明 |
|---|---|---|
| Emilia | 10 万小时级原始 | 多语言，需按流水线过滤清洗后取中英子集 |
| WenetSpeech | 1 万小时级 | 中文为主 |
| AISHELL-3 | 85 小时 | 中文多说话人，质量高，用于微调与评测 |

> UniVoice 使用了 30k 小时说话数据。本项目数据量缩水的补救手段是**热启动**（见 4.3），而非堆数据。

**歌声数据（目标百小时级）**

| 数据集 | 说明 |
|---|---|
| OpenCpop | 中文流行歌声，带音素级标注，DiffSinger 生态标准集 |
| M4Singer | 多歌手歌声集 |
| GTSinger | 多语言歌声，带精细标注 |

标注规范沿用 DiffSinger：DS 文件格式、音素-时间对齐、音素字典与合并组配置。

### 4.2 数据流水线（借鉴 Fish Audio S2）

```
原始音频 → 质量评估模型过滤 → 响度归一化 → ASR 富标注（转写+时间戳）
        → 强制对齐（音素级）→ 特征提取（mel/codec + 音色嵌入）→ 训练集
```

要点：质量评估模型与 ASR 模型在后续 RL 对齐阶段可直接复用为奖励信号（Fish S2 的多用途流水线设计），避免分布失配。

### 4.3 热启动策略（关键降本决策）

- Backbone **不从随机初始化训练**：以开源 CFM-DiT TTS 权重（F5-TTS 或 CosyVoice 系）热启动
- 仅新增的旋律编码器、null melody token、任务调制模块从零训练
- 预期效果：数据需求降低一个数量级，收敛速度显著加快

## 第五章 训练路线与里程碑

### M0 — 研究与复现验证

- **内容**：跑通 UniVoice（若已开源）/ Fish Speech / DiffSinger 的推理；完成一次小规模 LoRA 微调（Fish Speech 微调指南：音频+`.lab` 转写 → VQ token → protobuf 数据集 → LoRA 训练 → 合并推理）
- **算力**：租 1×4090（24GB）
- **验收**：三个项目各自推理出声；Fish Speech LoRA 微调后音色相似度主观可辨

### M1 — 数据流水线 + 冒烟训练

- **内容**：搭建 4.2 节流水线；用 ~10 小时说话 + ~10 小时唱歌做冒烟训练
- **算力**：租 1×4090
- **验收**：loss 正常收敛；合成音频可懂（字正确即可，不要求自然度）

### M2 — 0.3B 完整训练

- **内容**：全量数据（1k–5k 小时说话 + 百小时唱歌），热启动训练统一模型
- **算力**：租 4–8×A800，按周计
- **验收指标**：
  - 说话：PER ≤ 6%（参照：UniVoice 5.26%、F5-TTS 5.21%、CosyVoice3 5.30%）
  - 唱歌：PER ≤ 20%（参照：UniVoice 16.22%、Vevo1.5 24.72%）
  - 音色相似度：说话/唱歌跨模式同一参考音频的 speaker embedding 余弦相似度 ≥ 0.85
  - 主观 MOS ≥ 4.0（5 分制，10 人以上盲评）

### M3 — 对齐与部署

- **内容**：可选 DPO/GRPO 多奖励对齐（奖励信号复用数据流水线的质量评估模型，参考 Fish S2）；ONNX 导出；唱歌侧对接 OpenUTAU/DiffScope 编辑器生态（参照 DiffSinger 的 ONNX 导出路径）
- **验收**：对齐后 MOS 提升 ≥ 0.2；ONNX 模型在编辑器中可用

## 第六章 风险与备选

| # | 风险 | 触发条件 | 备选路径 |
|---|---|---|---|
| R1 | UniVoice 代码/权重未如期开源 | M0 时仓库不可得 | 基于 **F5-TTS**（开源 CFM-DiT TTS）自行扩展旋律条件模块与 null melody token——架构思想不变，工程基座替换 |
| R2 | 开源歌声数据量不足 | M1 唱歌分支不收敛或音高不稳 | 采用 **Vevo2 式无乐谱韵律 tokenizer**：从语音/歌声音频自动提取旋律条件做数据增广，降低对乐谱标注的依赖 |
| R3 | 租云成本超支 | M2 预算不足 | 降级为**双模型 LoRA 方案**：Fish Speech LoRA 微调负责说话 + DiffSinger 微调负责唱歌，两模型共享音色嵌入保证嗓音一致；先验证产品价值，再回头统一训练 |
| R4 | 热启动权重与新增条件模块不兼容 | M1 loss 异常 | 冻结 backbone 先训条件模块（适配器式），再整体解冻联合训练 |
