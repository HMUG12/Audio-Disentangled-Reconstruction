# ADR 全仓审计报告

- 日期：2026-10-31
- 版本基线：`pyproject.toml` 1.3.1（批次 67 收尾）
- 范围：`adr/`、`desktop/`（Tauri 2 壳 + 安装器）、`scripts/`、`docker/`、`third_party/gpt_sovits`（引用的部分）、全部依赖清单
- 重点：依赖、打包、兼容性；兼顾缺陷、安全、死代码、测试、性能

## 0. 方法与口径

八个维度按三个波次执行：

| 波次 | 内容 | 产出 |
| --- | --- | --- |
| 扫描 | 4 个并行子代理，分别负责「依赖与打包」「兼容性」「缺陷与安全」「死代码/性能/测试」 | 原始发现 63 条 |
| 去重归并 | 同一根因的多处证据合并为一条 | 57 条 |
| 对抗验证 | 每条发现由 3 个独立视角（正确性 / 影响 / 成本）投票，**严格 >2 票（即 3/3）才保留** | 保留 11 条，2/3 共 14 条进附录 A |

补充口径：

- 扫描代理只做检索与取证，不做结论；结论以主上下文复核源码为准。
- 验证过程中出现过两处代理误判，已按源码纠正（详见文末「验证纠错记录」）。
- 门禁状态：`check_versions.py` 9 项检查全部 1.3.1 通过；`check_compliance.py` 7 组门禁全部通过。**注意这两道门禁覆盖不到本报告中的大部分打包问题**（见 Q2）。

架构分层与风险区域：

```
adr/server   (FastAPI: v2/v3/openai 三个兼容层 + origin_guard + tts_cache + audio_codec)
adr/models   (GSV 引擎单例 + gsv_coalescer 跨请求合批 + 权重热换)
adr/services (SynthesisService: 参数校验/档案解析/合成收口)
adr/core     (settings 单源 env)
desktop/src-tauri (Tauri 2 壳，sidecar 托管 Python runtime，NSIS + Inno Setup)
scripts      (build_runtime 钉版、build_installer、check_* 门禁)
docker       (cpu/cuda 双变体镜像)
```

风险集中在两处：**对外分发链路**（打包配置、构建可复现性、镜像暴露面）与**对外协议契约**（OpenAI 兼容层、v3 overrides、缓存键）。内核（引擎、合批、流式）在批次 64–67 已被实测与 708 条测试覆盖，本次未发现新的高危内核缺陷。

## 1. 执行摘要

11 条保留发现：高危 3 条、中等 8 条。没有发现可直接导致数据崩溃或语法级错误的缺陷，但有三类问题会在**真实用户第一次接触时**直接暴露：

1. **默认部署即裸奔**：Docker 镜像默认监听 `0.0.0.0:9881` 且默认无鉴权。局域网内任何设备可直接调用合成、热换权重。
2. **OpenAI 兼容层不是 OpenAI 兼容**：`stream` 默认值与官方相反，`model`/`voice` 被当作 ADR 档案名解析，标准 SDK（`model="tts-1"`, `voice="alloy"`）必然 400。
3. **Tauri 壳的打包配置只覆盖了 Windows NSIS + ICO**：没有 `externalBin`/`resources` 声明，没有 macOS `icns` 引用，Tauri 打包产物与 `scripts/build_runtime.ps1` 生成的 runtime 之间缺少显式绑定。

一句话结论：**代码质量高于分发质量**。建议本轮优先修 3 项高危，把 8 项中等问题排入下一批次，2/3 项按附录 A 逐条决策。

## 2. 严重问题（3/3 一致保留）

### S1 [高] Docker 默认对外暴露且默认无鉴权

证据：

- [Dockerfile](file:///e:/新创意构思/新建文件夹/ADR/docker/Dockerfile#L124-L125) `ENTRYPOINT ["python", "-m", "adr.server"]` + `CMD ["--addr", "0.0.0.0", "--port", "9881"]`
- [docker-compose.yml](file:///e:/新创意构思/新建文件夹/ADR/docker/docker-compose.yml#L35) 端口映射 `"9881:9881"`（非 `127.0.0.1:9881:9881`）
- [app.py](file:///e:/新创意构思/新建文件夹/ADR/adr/server/app.py#L85) `enabled=not api_keys`：未设 `ADR_TTS_API_KEY` 时只靠 OriginGuard，而 [origin_guard.py](file:///e:/新创意构思/新建文件夹/ADR/adr/server/origin_guard.py#L56-L58) 对**缺少 Host 头**的请求直接放行，且 Origin 检查只对浏览器有效。

影响：容器部署在云主机/办公网时，任何能访问 9881 的进程（curl、Python 脚本、扫描器）都可调用 `/api/v2/tts`、`/set_gpt_weights`、`/set_sovits_weights`，属于「未授权算力占用 + 权重任意替换」。OriginGuard 的设计前提是「本机单用户」，在容器/服务器形态下不成立。

**口径修正**：容器内监听 `0.0.0.0` 本身不是缺陷——容器有独立网络命名空间，`0.0.0.0` 才能在端口映射后可达；真正的暴露面由 `ports:` 的发布地址决定。初版本报告的「镜像内改 `127.0.0.1`」建议是错的（那样宿主机完全连不上），已废弃。

建议（按成本递增）：

1. compose 默认回环发布：`ports: ["127.0.0.1:9881:9881"]`，需要局域网时由用户显式改，并同时设 `ADR_TTS_API_KEY`。
2. 示例统一：`README.md` / `docker/README.md` 的 `docker run -p 9881:9881` 改为 `-p 127.0.0.1:9881:9881`，紧随其后标注「对外暴露必须设 `ADR_TTS_API_KEY`」。
3. 启动告警保留：`adr.server.__main__._warn_unauthenticated_listen` 已覆盖「0.0.0.0 + 无 key」场景，无需新增代码。

### S2 [高] OpenAI 兼容层与官方 SDK 不兼容

证据：

- [openai_compat.py](file:///e:/新创意构思/新建文件夹/ADR/adr/server/openai_compat.py#L38) `stream: bool = True` —— OpenAI 官方 `/v1/audio/speech` 默认 `false`。
- [openai_compat.py](file:///e:/新创意构思/新建文件夹/ADR/adr/server/openai_compat.py#L90-L91) `"profile": body.model, "voice": body.voice` —— 直接把标准字段当 ADR 档案名（字段注释自述 `model` 即「音色档案名」）。
- [v2_compat.py](file:///e:/新创意构思/新建文件夹/ADR/adr/server/v2_compat.py#L88-L101) `_resolve_profile` 对非空 profile 无默认回退，加载失败即 400。

影响：用户按官方文档写 `client.audio.speech.create(model="tts-1", voice="alloy", input="...")`，得到的是 `ProfileNotFoundError` 的 400；即便传了合法档案名，返回体默认是流式，而官方 SDK 期望一次性 JSON/二进制。这是「宣称兼容但实际不可用」，会直接消耗首次试用。

建议：

- `model` 与 `voice` 做映射层：`tts-1`/`tts-1-hd` → 忽略或映射到默认档案（`app.state.default_profile`），`voice` 仅在命中档案时作为 profile，未命中时回退默认档案而非报错。
- `stream` 默认改为 `False`，与官方对齐；需要流式时显式传 `true`。这会改变既有行为，需在 `docs/tts-api-spec.md` 记录并升 minor。
- 补一条端到端测试：用 `openai` Python SDK 指向本地服务，断言 200 + 非空音频。

### S3 [高] Tauri 打包配置不完整

证据：

- [tauri.conf.json](file:///e:/新创意构思/新建文件夹/ADR/desktop/src-tauri/tauri.conf.json#L18-L19) `"targets": ["nsis"]`、`"icon": ["icons/icon.ico"]`
- 配置中**没有** `bundle.externalBin`，**没有** `bundle.resources`；`icons/icon.icns` 已生成但未被引用。
- [installer.iss](file:///e:/新创意构思/新建文件夹/ADR/scripts/installer/installer.iss#L48) 另行指向 `..\..\desktop\src-tauri\icons\icon.ico`，与 Tauri 的 NSIS 产物是两条独立安装链路。

影响：

1. sidecar 形态的 Python runtime 没有通过 `externalBin`/`resources` 声明，安装包内容依赖外部脚本手工拼装。
2. 配置宣称了 `targets: ["nsis"]`，但 NSIS 因 ~2GB 数据上限根本不可用（[build_installer.ps1](file:///e:/新创意构思/新建文件夹/ADR/scripts/build_installer.ps1#L2-L3) 自述），实际链路是 `--no-bundle` + Inno Setup。配置与现实不一致，后来者直接 `npx tauri build` 会踩空。
3. macOS/Linux 交付路径实际不存在（无 `icns` 引用、`targets` 仅 nsis）。

**口径修正**：CPU/GPU 两包共用同一 `AppId` 是**有意设计**（[installer.iss](file:///e:/新创意构思/新建文件夹/ADR/scripts/installer/installer.iss#L15) 注释：GPU 包装在 CPU 包上 = 原地升级 runtime，不产生双份安装）。初版建议「拆分 AppId」会破坏该升级语义，已废弃。

建议：以 **Inno Setup 为唯一安装器**，Tauri 退化为 exe 构建器——

1. `tauri.conf.json` 关闭 bundler（`bundle.active = false`），删除 `targets` / `windows.nsis` / `licenseFile` 等只对 bundler 生效的键；
2. `build_installer.ps1` 头注释明确「Tauri 只产 `adr-desktop.exe`，安装包由 Inno 组装 runtime」；
3. `externalBin`/`resources` 不再需要（runtime 由 `installer.iss` 的 `[Files]` 载荷），macOS 交付需另立批次（含签名链）。

## 3. 质量问题（3/3 一致保留）

### Q1 [中] 构建不可复现

- [build_runtime.ps1](file:///e:/新创意构思/新建文件夹/ADR/scripts/build_runtime.ps1#L55) 从 GitHub `releases/latest` 取 python-build-standalone —— 同一脚本在不同日期产出的解释器不同。
- [build_runtime.ps1](file:///e:/新创意构思/新建文件夹/ADR/scripts/build_runtime.ps1#L149) `chardet` 未钉版（同文件其余依赖全部 `==`）。
- [build_installer.ps1](file:///e:/新创意构思/新建文件夹/ADR/scripts/build_installer.ps1#L36) `npx -y @tauri-apps/cli@2` —— 主版本浮动，需联网。

建议：解释器 URL 与 SHA256 钉死（与 `GSV_COMMIT` 同思路）；`chardet` 补 `==`；CLI 改为 repo 内 `devDependencies` 的 `@tauri-apps/cli` 固定版本，从 `node_modules/.bin` 调用。

### Q2 [中] 出包流程未跑版本/合规门禁

- [build_installer.ps1](file:///e:/新创意构思/新建文件夹/ADR/scripts/build_installer.ps1#L26-L31) 只调用 `check_runtime.py`；`check_versions.py`、`check_compliance.py` 未进入出包链路（仅在人工/CI 单独跑）。

影响：批次门禁形同建议。本次审计即发现版本面漂移（见附件 A-3）正是门禁未覆盖 Docker/文档所致。

建议：`build_installer.ps1` 前置调用两道门禁，失败即 `exit 1`。

### Q3 [中] `check_runtime.py` 默认路径不存在

- [check_runtime.py](file:///e:/新创意构思/新建文件夹/ADR/scripts/check_runtime.py#L34) `DEFAULT_RUNTIME = REPO / "build" / "runtime"`，实际产物目录为 `build/runtime-cpu` 与 `build/runtime-gpu`。

影响：不带参数直跑必然 FAIL，给出误导性结论；也让 Q2 的「加上门禁」变得无效（一加就红）。

建议：默认路径改为探测 `runtime-cpu`/`runtime-gpu` 并取存在的那个。

### Q4 [中] pandas 为隐式依赖，容器清单缺失

- [dataset.py](file:///e:/新创意构思/新建文件夹/ADR/third_party/gpt_sovits/GPT_SoVITS/AR/data/dataset.py#L10) `import pandas as pd`
- [requirements-linux.txt](file:///e:/新创意构思/新建文件夹/ADR/docker/requirements-linux.txt) 无 `pandas`；`pyproject.toml` 核心依赖亦无。

影响：AR 训练/数据路径在容器内 `ImportError`；本地能跑是因为整机环境恰好装了 pandas，属于「开发机掩盖缺陷」的典型。

建议：若容器不提供训练能力，则在容器启动时显式提示「训练功能不可用」并在文档声明；若要支持，则把 `pandas` 钉版进 `requirements-linux.txt`。二者选一，不要维持隐式状态。

### Q5 [中] TTS 缓存键无格式/编码版本

- [tts_cache.py](file:///e:/新创意构思/新建文件夹/ADR/adr/server/tts_cache.py#L68-L71) `make_key` = `sha1(json(payload))`，`payload` 只含 `_KEY_FIELDS`，无 `CACHE_VERSION`。
- [tts_cache.py](file:///e:/新创意构思/新建文件夹/ADR/adr/server/tts_cache.py#L83-L125) 磁盘缓存跨版本重建（`_disk_load_locked` 只按 mtime 排序）。

影响：一旦编码参数（如 `pack_audio` 的 mp3 码率、重采样实现）或关键字段集合变化，旧缓存仍会命中并返回旧格式音频，且无失效手段（除手动清目录）。升级后「音质没变」类问题极难定位。

建议：在 `make_key` 的 payload 中加入 `CACHE_VERSION`（常量，随音频编码/字段集变化递增）；启动扫描时丢弃未知版本前缀的磁盘条目。

### Q6 [中] v3 overrides 大部分被静默忽略，且无 NaN/Inf 校验

- [v3_compat.py](file:///e:/新创意构思/新建文件夹/ADR/adr/server/v3_compat.py#L315-L319) 收集 `overrides`（含 `speed_factor`/`temperature`/`top_k`/`top_p` 等）。
- [v3_compat.py](file:///e:/新创意构思/新建文件夹/ADR/adr/server/v3_compat.py#L204-L222) `_produce` 只读 `voice.get("sampling")` 里的 `top_k`/`top_p`/`temperature`，**不读 overrides，也不传 `speed_factor`**。

影响：调用方按文档传 `speed_factor=1.2` 得到 1.0 的音频，且无任何告警。与 v2 的 `_bad_number` 闭区间校验相比，v3 缺少 NaN/Inf 拦截（`float('nan')` 会穿透到引擎）。

建议：把 `overrides` 合并进 `sampling` 解析（显式 overrides 优先于档案），复用 v2 的 `_bad_number` 做区间与有限性校验，非法值返回 400 而非忽略。

### Q7 [中] 非流式响应的编码与缓存写盘仍在事件循环

- [v2_compat.py](file:///e:/新创意构思/新建文件夹/ADR/adr/server/v2_compat.py#L319-L336)：合成已 `asyncio.to_thread`，但 `pack_audio(BytesIO(), ...)` 与 `tts_cache.put(...)` 在事件循环线程里同步执行。

影响：`media_type` 为 mp3/aac/ogg 时走 ffmpeg 子进程同步等待，单请求即可阻塞整个事件循环（含 `/health`、流式首包）。缓存落盘（`write_bytes` + `os.replace`）同样同步。

建议：把 `pack_audio` + `tts_cache.put` 一并放进同一个 `to_thread` 块；或编码在线程池、`put` 改为 `run_in_executor`。改动小，收益直接（并发下的 P99）。

### Q8 [中] 合批组内 assert 使同组请求全部失败

- [gsv_coalescer.py](file:///e:/新创意构思/新建文件夹/ADR/adr/models/gsv_coalescer.py#L608) `assert text_lang in tts.configs.languages`
- [gsv_coalescer.py](file:///e:/新创意构思/新建文件夹/ADR/adr/models/gsv_coalescer.py#L284-L300) 组级 `try/except` → `_reset_models` + 该组所有 Future 报错。

影响：同一签名组内只要有一条请求带非法 `text_lang`，同组其余正常请求一起失败。影响范围限于该组（非全服务），但属于「一个坏请求拖垮同批」的错误隔离粒度问题；且 `assert` 在 `python -O` 下会被移除，行为随运行方式改变。

建议：把语言校验前移到请求入口（v2/v3 参数校验阶段，返回 400），合批层不再依赖 `assert`；若必须保留，改为显式 `raise ValueError`。

## 5. 测试缺口

| 风险点 | 现状 | 建议用例 |
| --- | --- | --- |
| OriginGuard 边界 | 有中间件但缺少「缺 Host」「带点域名」「`Origin: null`」的显式用例 | 参数化 6 组 Host/Origin 组合，断言 403/放行 |
| OpenAI 兼容层 | 无官方 SDK 端到端 | `openai` SDK → 本地服务，断言默认非流式、未知 model 回退默认档案 |
| v3 overrides | 无「传了是否生效」的断言 | 传 `speed_factor=1.2`，断言输出时长比 1.0 短（允许容差） |
| 缓存版本 | 无 | 构造旧 key 的磁盘条目，断言升级后被丢弃 |
| 打包链路 | 无 CI 冒烟 | `build_installer.ps1 -DryRun`：只跑门禁 + 校验产物存在，不实际编译 |
| 容器依赖完整性 | 无 | 容器内 `python -c "import adr.training..."` 冒烟，或显式 skip 标记 |
| 合批错误隔离 | 有组级测试，缺「同组一坏多好」 | 1 条非法 `text_lang` + 2 条合法，断言 2 条成功（修复 Q8 后） |
